## Decision summary

The owner decided to build Orbit: a Go CLI that runs coding agents in sandboxes on OrbStack, as the OrbStack counterpart of Docker Sandboxes (D02, D13). That decision is agreed. The sandbox is one OrbStack isolated machine per project directory; agents and Git worktrees run inside it (D12, D18). Root in that machine owns the firewall and the egress proxy; the agent is an unprivileged user with rootless Docker and no sudo (D14).

The owner uses OrbStack on macOS and reports that Docker Sandboxes do not support it (see Problems). There is no workaround on record.

The first scope is one complete job: initialize a sandbox for one project directory with Claude Code in it, enter it, use the subscription of the user, and not reach the rest of the host (Scope, D19, R10, R03, R08).

Three unknowns can change the design. An isolated machine shares the OrbStack kernel, which is weaker than the microVM of Docker Sandboxes; the owner accepted that limit (A01, D12). The egress design of D14 held in a spike under stated conditions (A05). The sign-in was tested only up to the code exchange (A02). R08 added a fourth: forwarding the host SSH agent into an isolated machine. An agent-run `ssh -T git@github.com` showed that the forwarded socket and the SSH path to GitHub work; authenticated use was not shown (A06).

The earlier `orb-sbx` design optimizes for the opposite goal: reuse of the host engine, with an opt-in host Docker socket and SSH agent forwarding. Where it conflicts with today's request, this brief follows the request (D09) and keeps the conflicts as questions (Q05–Q07).

Next action: build `orbit init` and `orbit shell` (backlog items E01-S01 and E01-S02), then the owner's first full `/login` in a sandbox, which A02 did not cover. No dates are set.

## Scope

- **Now:** on macOS with OrbStack, in a project directory: initialize one sandbox for that directory with Claude Code installed, enter it with a shell, authenticate with the subscription of the user (D08), and stop, start, and destroy it; list all sandboxes (D18, D19). The host SSH agent is forwarded by default (R08). Outbound network is deny-by-default with a fixed default allowlist (R01, R03, R07, D12, D14). A GitHub App identity for the agent (D10).

## Key flows

- Current state: the owner cannot run Docker Sandboxes on OrbStack; no other flow is on record. `[DOCUMENT]` owner request, 2026-11-10
- Future state (D08, D12, D14, D16, D18, D19): in a project directory, `orbit init --agent claude-code` creates the sandbox of that directory, shares only that directory, and installs Claude Code; `--no-ssh-forwarding` leaves the host SSH agent out (R08). `orbit shell` opens a shell as the agent user, where the user starts `claude`. On first use the user logs in with `/login`; the login persists on the disk of the sandbox. `orbit stop`, `orbit start`, and `orbit destroy` act on the sandbox of the current project directory. `orbit ls` lists all sandboxes. There is no `orbit run`. `[DOCUMENT]` owner decision, 2026-11-10
